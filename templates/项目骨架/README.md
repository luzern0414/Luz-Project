# 〔项目名称〕

〔用一句话概括使用对象、业务场景与核心任务。示例为健身门店提供会员登记、到店核验和课程预约。〕

## 项目用途

- **使用对象** 〔填写主要使用者及使用端〕
- **主要功能** 〔填写两到三项已经确认的功能〕
- **使用入口** 〔填写可公开的入口、试用方式或负责对接的角色〕

## 本地启动

| 步骤 | 填写内容 |
|---|---|
| 准备环境 | 〔填写运行所需的语言、工具及实际版本〕 |
| 安装依赖 | 〔填写从项目根运行的安装命令〕 |
| 设置配置 | 按[配置说明](#配置)选择环境，再根据 `.env.example` 注入需要的环境变量 |
| 初始化数据 | 项目采用数据库时，按[数据库迁移说明](infra/README.md)执行项目的迁移命令 |
| 启动和验证 | 〔填写启动命令、访问地址与最小验证步骤〕 |
| 执行测试 | 〔填写日常检查或测试的实际命令〕 |

## 目录说明

| 目录 | 内容 |
|---|---|
| `src/` | 主要代码，按实际产品端或模块组织 |
| `config/` | 配置入口与受版本管理的配置文件 |
| `infra/migrations/` | 项目实际采用的迁移脚本，执行说明放在 `infra/README.md` |
| `docs/01-原始资料/` | 客户原件、现场资料和原始回填 |
| `docs/02-对接资料/` | 需求、方案、报价、协议、使用和验收文件 |
| `docs/03-开发资料/` | 功能、技术、测试、上线和运维材料 |
| `log/` | 本地运行记录 |

## Git 协作

- 在项目 README 填写实际默认分支、评审方式和维护人。任务分支沿用仓库命名约定。Codex 新分支示例为 `codex/booking-limit`。
- 每个提交写明一项变更及其目的。主题示例为 `fix: 修正预约余位校验`。关联的迁移、配置与使用说明随对应变更一起评审。
- 提交前核对 `git status` 与 `git diff --staged`。通常提交源码、锁文件、迁移、可共享配置和开发文档。原件、商务资料、真实凭据、日志和业务数据按项目授权存放，默认规则见[忽略清单](.gitignore)。

## 配置

项目以 `config/config.toml` 登记使用的配置来源、负责人、检查和生效方式。普通参数在 `config/` 内维护，带凭据的值通过环境变量或受控密钥来源注入。变量名见[环境变量示例](.env.example)。

| 用途 | 示例 | 本项目 |
|---|---|---|
| 配置来源 | `config/runtime/` 保存应用的基础值和环境差异 | 〔填写项目采用的组件、环境与来源文件〕 |
| 秘密引用 | 数据库连接引用 `LUZ_DATABASE_URL` | 〔填写实际引用名、负责人与注入方式〕 |
| 检查和生效 | 检查通过后按配置登记的方式使变更生效 | 〔填写实际命令、影响和回退方法〕 |

采用 Luz-Dev 配置包时，先用 `config_bundle.py init` 在独立的新目录生成，再把项目采用的配置合入 `config/`。配置和日志的实际检查按 Luz-Dev 的 `configuration-entry.md` 执行。
