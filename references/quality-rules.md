# UX、DX、AX 具体规则与评估

唯一规则库是 `quality-rules.json`，查询工具是 `../scripts/quality_rules.py`。每条规则有稳定编号、负责技能、阶段、适用范围、依据类型、指标和单位、例外、验证方法、所需证据及严重性。按当前任务选择适用规则，不把所有领域检查塞进一个简单改动。

UX 是用户完成任务的体验；DX 是开发、排障和维护的体验；AX 是 Agent Experience，智能体发现、执行、观察和恢复任务的体验。无障碍可为人和智能体提供可靠语义，但不等于 AX。当前研究不支持声称存在统一 AX 国际评分。

## 来源与阈值

`standard` / `specification` 只约束注明版本和范围；`vendor` 是厂商实践；`user-policy` 是用户明确规则；`local` / `local-derived` 是 Luz 的实施选择。来源中的 SHOULD 不改写成 MUST，示例不改写成通用阈值。来源记录保留实际归档、哈希、发布主体、版本定位及章节，研究记录保存短引文和采用/排除理由。

例如：网页点击目标、对比度和重排按对应 WCAG 条款与例外；Carbon 图例尺寸仅适用采用该模式的图表；Google 的小变更示例不是通用代码行数限制；DORA 指标不用于个人排名；MCP 规则按协商的具体版本适用。这里覆盖若干选定条款，不能据此宣称完整 WCAG 合规。

本地的 100% 追踪、自研交互逐项验证、0 个未知阻断是流程目标。任务成功率、延迟、成本、RTO/RPO 等产品预算应由 System 在采样前确定；不得把本地目标冒充厂商标准，也不能事后换分母宣布达标。

## 按阶段执行

```powershell
python -X utf8 D:\Codes\Luz-Project\scripts\quality_rules.py list --owner luz-design --stage design
python -X utf8 D:\Codes\Luz-Project\scripts\quality_rules.py show UX-05
python -X utf8 D:\Codes\Luz-Project\scripts\quality_rules.py plan --owner luz-design --stage design --out <raw中的新评估文件.json>
python -X utf8 D:\Codes\Luz-Project\scripts\quality_rules.py check <评估文件.json>
```

`plan` 只创建 pending 计划，不会填写通过。领域技能负责填写真实观察和证据，Ops 在交付阶段复核全部相关领域的交接。Project 管审批和范围，不能替领域技能作质量结论。

| 负责技能 | 先检查的规则 |
|---|---|
| System | 需求依据、完整映射、状态、指标口径、图表数据及AI能力边界 |
| Design | 框架/本地复用/适配、完整页面、可访问语义、适用标准与智能体定位 |
| Dev | 构建、合同、变更、真实复用量、工具和API、权限、错误和恢复 |
| Ops | 真实执行、当前证据、三轴结果、性能、交付指标、回滚和未覆盖范围 |
| Project | 三轴取舍、具体批准、阶段路由和技能入口 |
| Crawl | 本地缺口的线上来源、正文/版本/许可和来源分类 |
| Writing | 一致术语、清晰动作、必要状态说明和恢复文案 |

## 评估记录

每份 `luz-quality-assessment/1` 绑定当前规则库哈希和精确 owner/stage；逐条填写 pass / fail / pending / not-applicable。pass 必须有实际观察、审阅者和真实文件 path/SHA-256；not-applicable 必须说明具体范围原因和审阅者，不计通过样本。关键未测项是 pending，不是 not-applicable。advisory 的失败或未测保留显示，不自动变成通过。

Design 的整体审阅还必须引用评估文件的 path/SHA-256，评估根字段 `receipt_sha256`、`browser_report_sha256` 必须对应当前包及浏览器报告，scope 固定 `luz-design/design`。现有逐页逐宽度截图、UX/DX/AX 观察和阻断清单继续保留。只写“三轴通过”、复制上个版本的观察或换个阶段的评估均无效。

检查器验证结构、完整覆盖和文件一致性，不能证明观察真实、视觉美观、许可适用或没有所有缺陷。语义审查仍须真实执行任务、阅读报告和查看页面。规则校验成功不等于用户业务验收。

## 可比较的指标

| 对象 | 具体报告内容 | 防止误用 |
|---|---|---|
| 用户任务 | 已成功任务数/预定任务尝试数，失败分类，完成时长分布 | 先固定成功结果、人群、设备、版本和窗口；取消、未完成如何计入事先写明 |
| 开发反馈 | 安装/构建/本地测试/CI分别记录样本数、p50/p95和失败率 | 固定硬件和缓存条件；小样本说明限制，不以单次速度代表稳定改善 |
| 智能体任务 | 任务成功率、耗时、调用次数、token、工具错误和副作用 | 固定任务/模型/工具/数据版本；允许有效替代路线，记录最终状态，不能以少调用掩盖失败 |
| 组件复用 | 独立组件分母；原样、配置、绑定、有依据的自研的多标签计数 | 标签可重叠，不相加；同组件重复挂载不虚增数量，避免100%配额诱导误选 |
| 已上线服务 | DORA五项和实际事故/部署数据、性能实测范围 | 无生产数据标未测；不用于个人排名，不用实验室结果替代真实用户分布 |

重要决定逐轴写收益、中性、退步或不适用及依据。只有宣称改善的轴需要可比基线；中性如实记中性。实质退步先调整方案，必要取舍交用户针对具体内容决定。不能把三轴平均分当作放行依据。

## 更新和失效

来源版本、已批准需求、组件源码、规则库、当前产物或运行证据变化时，重新审查受影响内容。旧评估的目录哈希失配会阻止复用；可据差异复核未受影响项后生成当前评估，不能静默删除规则或直接改哈希。用户正式文件批准、新手写组件批准、部署授权仍走各自合同，内部质量审查不增加一轮用户审批。
