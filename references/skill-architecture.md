# Luz 技能架构与完整开发链路

本规范来自用户确认的工作方式：有依据的需求、统一框架、优先复用、实际验证。Project 管流程，领域技能对各自产物负责；Crawl 提供证据，Writing 管事实表达和术语。外部案例只能支持方法或候选，不能替客户创造业务事实。

## 用户的共同硬规则

七个技能每次都执行，规则卡开头原样带出本节，各技能的经验库不再重复记录。当前用户指令与本节冲突时按当前指令，并更正本节。

1. **中文优先。** 说明、报告和界面文案用中文；代码、命令、路径、字段、固定协议值、必要专名和核对用的原文保留原样，缩写首次出现给中文含义。
2. **简洁。** 标题短、单行、不带括号说明；不写没人要的建议、下一步、口号和装饰；只交付用户要的内容，过程信息留在 `raw`。
3. **按需检索。** 用户要求搜索时按约定数量阅读去重正文。尚需核实的外部事实按缺口查证；简单代码修改、直观问题或给定材料足以回答时直接处理。生成器需要阶段记录时，可用本地依据通过检查。联网阶段的数量、引用与核验见 Luz-Crawl 的 evidence-policy.md。
4. **用真实模板和成熟组件。** 正式文档与界面实际选择并使用 Luz-Design 模板；界面只表现已确认的功能，主题、组件和图标由任务决定，不设双主题、组件数量、按钮必带图标之类的配额。
5. **客户只收 PDF 和 Excel。** HTML 只给开发与评审；每份客户文件内容自足，不互相引用；预算、人日、报价默认不写，报价数字只来自人工。
6. **产出位置。** `E:\Skill输出\<技能>\NNN-主题\`：`raw\` 放源文件和过程文件，同级是汇总页；一个需求一个会话目录，只告诉用户一个要打开的文件；项目目录只放成果。
7. **审批。** 不代用户或客户批准，沉默不是批准；项目里用户只逐个审批 `docs` 文件，内部步骤必须做完，但不向用户罗列。
8. **阅读页。** 文字层级按 Markdown 字阶，桌面正文 18、手机 16，样式母本是 Luz-Design 的 `md-type.css`；每个 HTML 都有实心页签图标。
9. **沉淀。** 结束前写入或确认经验：只属于一个项目的要求标 `project`，维护技能自身的经验标 `maintenance`，已写进规范页的标 `codified`。

## 一、职责与唯一来源

| 技能 | 决定与执行 | 必须交接 | 不替谁做决定 |
|---|---|---|---|
| Project | 项目结构、交付文件定义、阶段路由、文件审批、变更、追踪和恢复 | 状态根、批准版本、待办、阻塞及交接索引 | 不代写业务逻辑、不代签人工审批 |
| System | 用户任务、业务模块及规则、各端主入口、数据、动作、权限与状态 | 功能表、入口表、`ui-requirements.json`、行为验收条件 | 不为适配模板删功能，不规定视觉取值 |
| Design | 页面与原型的视觉框架、组件、设计令牌、文档模板、排版与成品检查 | 复用计划、实际来源、适配记录、完整 UI 包及当前浏览器证据 | 不改需求，不把库名、截图或标记当成复用 |
| Dev | 技术实现、接口与数据、权限、服务、集成、迁移及可复现构建 | 实际代码、接口绑定、依赖锁、测试、环境与迁移说明 | 不悄悄换设计，不把演示数据当生产实现 |
| Ops | 独立验证、回归、发布准备、监控、备份、恢复与交付 | 当前版本证据、风险、发布/回滚方案、验收矩阵 | 不把截图当任务完成，不替用户发布或最终验收 |
| Crawl | 问题驱动检索、原文采集、组件候选、源代码获取线索与证据核验 | 逐字摘录、发布主体、覆盖、来源版本、失败路线与限制 | 不宣称搜索结果已获准复用，不替领域技能选方案 |
| Writing | 事实整理、受众、术语、操作文案与正式文字 | 声明表、术语/文案键及简洁正文 | 不编业务事实、不扩功能、不添加装饰性标语 |

System 在 [系统设计](../../Luz-System/references/system-design.html#module-boundaries)与[入口规范](../../Luz-System/references/ui-standards.html#entry-ownership)决定模块、规则和入口。Project 在[项目目录](project-structure.md)、[客户文件](client-documents.md)和[开发矩阵](development-matrix.json)定义项目文件。Design 的[文件设计](../../Luz-Design/references/file-design.html)负责模板与排版，[文档证据](../../Luz-Design/references/document-evidence.md)负责正文来源表达和成品核对。检索按 Crawl 的[依据合同](../../Luz-Crawl/references/evidence-policy.md)，审批按 Project [操作手册](runbook.md)。

每项规则只在负责技能维护。交接只传已确认文件、稳定编号、必要字段、证据与版本，消费方读取本次需要的公开合同或命令。独立任务可从本技能入口执行。只有实际需要对方的模板、证据或批准产物时才连接对应入口。

每个技能保留四层：短 `SKILL.md` 负责触发与调用协议；规则卡只加载本任务相关规则；references 定义领域合同；scripts 实施能机械验证的检查。经验记录有适用范围、确认日期及被替代关系，不能让历史偏好重新覆盖当前明确指令。

## 二、完整流程

| 步骤 | 输入与具体动作 | 完成条件与下一手 |
|---|---|---|
| 0 接管现状 | Project 读取当前目录、状态、已批准文件、未提交修改、运行方式和现有检查。区分事实、用户约束、假设、待核实项 | 明确当前阶段和已有授权；保留回退点；已有产物不凭文件名判过期 |
| 1 明确目标 | System 先写用户是谁、触发场景、要完成的任务、成功结果、不做什么；Project 确认范围 | 每个需求有用户材料、现有系统或实际研究依据；假设明确标记，关键未知保持阻塞 |
| 2 依据 | 依原始请求判断材料够不够，按证据缺口核验 | 本地阶段记录其依据并检查。联网阶段读正文、写结论并检查，数量和覆盖按 Crawl 证据合同 |
| 3 System 契约 | 拆功能、页面、入口、主动作、状态、数据、权限、结果与恢复；列需要的组件能力 | `ui_requirements.py` 校验双向映射、引用和缺口；读页面可没有操作，不制造假按钮满足检查 |
| 4 框架先行 | Design 从成熟页面框架及现有实现中选择统一导航、页面区域、内容宽度、层级、响应式与令牌策略 | 先有能解释全部主要任务的框架方案，再放组件；明确框架来源、适用性和兼容约束 |
| 5 本地复用 | 逐项查询真实本地组件、页面模板与已有项目实现；阅读源码、样例、依赖、状态和许可 | 每项登记采用/淘汰理由、真实文件和哈希、承担的组件能力；不能仅登记目录编号 |
| 6 网络补齐 | 对具体本地缺口，Crawl 搜索成熟组件，记录查询、官方链接、版本、许可、源码/资产和兼容性 | 候选链接可检索；采用组件必须实际取得并验证。候选目录与项目准入分开，不“有链接即完成” |
| 7 适配与自研 | 统一适配文字、颜色、图表数据和组件原生配置；布局、内容组件与业务连接按 Design 组件合同自由实现 | 复杂控件优先成熟实现；确需自研时记录理由、查过的来源和针对性验证。用户限定了修改范围的任务按他的范围做，超出范围先问 |
| 8 贯通与实现 | 先完成一条代表性完整任务，再补其它页面与状态；Dev 接入真实数据、权限、服务和异常恢复 | 行为与批准需求对齐，依赖锁定，可复现构建；UX/DX/AX 同时核查。原型与生产实现分别声明 |
| 9 独立验收 | Ops 对当前产物验证成功、失败恢复、取消、重复提交、权限与数据保留；Design 审查完整页面及跨页一致性 | 浏览器操作和结果证据绑定当前构建；截图只证明相应渲染。再核查具体平台、环境及未覆盖范围 |
| 10 交付与回流 | Project 生成同源正式文件，逐文件审批，确认变更已关闭；Ops 执行获授权的发布/移交；各技能写 note | 当前文件、来源、证据和审批哈希一致；未完成项不包装成完成；把适用经验回流到负责技能 |

本阶段内部命令不重复创建研究任务。小改动按影响范围复验，已有授权不重复询问；未批准的业务文件、真实发布和最终验收的人工门禁照常。

上述 0—10 步是七技能共同生命周期，独立调用按实际范围取适用步骤，不自动创建项目。工具准备、读卡、只读检查、同阶段回归和已授权技能源码修复不递归调用 Crawl；正式业务内容、设计决定、实现与验收前必须完成本阶段研究。调用下级模板或第三方专项技能时传递本阶段问题、证据和输出合同，不重复建立一串无关研究任务。遵守用户对并发、范围与工具的当前限制。

本机其他业务技能（例如 PDF/Word、前端、平台 SDK、部署专项）调用前同样由最相关的 Luz 领域负责人承接本阶段 Crawl：文档排版归 Design、文字归 Writing、实现归 Dev、验收运维归 Ops、需求功能归 System。已完成同阶段证据作为上下文传入专项技能，不因嵌套工具调用重新计数；出现新业务阶段或关键问题则补齐对应研究。维护其可执行的本地入口，不直接改第三方插件缓存；系统约束与用户当前明确要求优先。

### 系统完整性：每个功能都能走通

每个在范围内的稳定 FN-ID 在现有功能表/交接合同中明确：用户与触发条件 → 权限及前置状态 → 页面/入口/动作 → 输入与校验 → API/实体与数据变化 → 成功状态 → 失败、取消与恢复 → 验收用例与证据。纯阅读功能不强造写入 API；不适用项说明理由。接口和库表从真实实现/明确方案取得，不能从 UI 截图猜造。

System 先列任务全貌、上下游、角色权限、实体和状态不变量，再拆页面；Design 用共享框架、术语、组件状态、令牌与导航支持这些任务；Dev 实现事务/并发/重复操作语义；Ops 对同一功能链逐项验证。跨功能至少核对相同对象的名称/标识、状态转换、数据口径、权限、错误文案、恢复路径与空/加载/失败状态。需求变更沿链路更新，不能只改当前页。

架构采用适用的上下文、容器/组件、部署和运行场景视图；没有阅读价值的层级不凑图。关键决定记输入约束、备选、理由、后果与复核条件；同一决定只维护一处，其余引用。重点运行场景包含主任务、外部集成、故障恢复及运维操作；质量要求使用质量规则库的场景、单位、环境与可测响应，不能只写“高性能、可扩展”。

方法依据：C4 [图的层级](https://c4model.com/diagrams)、arc42 [运行视图](https://docs.arc42.org/section-6/)、[架构决定](https://docs.arc42.org/section-9/)、[质量场景](https://docs.arc42.org/section-10/)，2026-11-08 核对。本地 FN 映射与门禁来自用户要求，外部资料不规定这些字段。

## 三、UI 模式与复用顺序

默认 `component-reuse`：System 行为合同 → 有来源的统一框架 → 本地组件 → Crawl 网络补齐 → 统一适配 → 整体验证。可运行的界面包由 Design 的 `frontend.py` 构建、`ui_package.py` 检查，细则只在 [Design 组件合同](../../Luz-Design/references/component-reuse.md) 维护。

用户明确要求严格沿用已有界面时：保留原件的构图、组件和资产，只改他允许的部分；功能对不上就另选来源或记录缺口，不改原件来补。已登记的来源锁定包继续按原合同核验，交接要求见 Design 的 `references/ui-ownership.md`。

已有的定点维护或项目定制授权只覆盖原记录的项目与范围，不是全局豁免。历史产物保持原来的模式，不靠补一个字段迁到更宽松的规则。

## 四、UX／DX／AX 是同一决定的三个检查面

AX 在此明确指 **Agent Experience，智能体体验**。无障碍是 UX 与 AX 的共用基础，不能代替 AX。

| 面向 | 要观察的结果 | 验证方式 |
|---|---|---|
| UX 用户 | 能找到入口、理解状态、完成任务、从失败恢复；内容有主次、必要标签明确 | 完整旅程、键盘/触屏、窄屏、错误与空状态、保存后重进、取消/撤销；真实页面审阅 |
| DX 开发者 | 来源清楚、依赖可维护、少一套实现、变更范围明确、能定位失败 | 组件/源码/许可清单、锁文件、重复实现检查、行为合同与接口绑定、构建及回归命令 |
| AX 智能体 | 可发现动作、识别对象/状态、观察结果、恢复或安全停止 | 语义定位、稳定对象 ID、结构化接口/错误、明确授权边界、重复操作策略及真实任务结果 |

每个影响架构、组件或交互的重要决定逐轴记录收益、中性、退步或不适用及依据；宣称改善的轴提供可比基线，中性不冒称提升。不能用“更高级”“更智能”充数，也不凭数字打分宣称同时提升。某方面发生实质退步时先寻找更简单方案；确实存在未授权取舍时把具体冲突交给用户，不能静默牺牲。

简洁标准：一个页面有清楚目标；能删的装饰性标语、重复说明、次要标签直接删；若只能靠长说明才能看懂，先调整布局、命名和任务顺序。保留必要标签、单位、权限、状态、错误恢复及后果说明。默认不添加无任务依据的仪表盘、卡片、徽章、主题开关、动画或图表。

图表从用户问题、指标定义、数据来源、时间范围与单位出发；不得为好看编数字或改变含义。颜色使用共享语义令牌，不用多库拼出多套视觉。模型按已确认功能、任务和统一规范决定主题、组件与图标；删除全局双主题、至少六种组件和按钮一律带图标等配额。验收看功能是否清楚、操作是否可用、页面是否完整一致，不按装饰数量打分。

说明、报告和界面文案尽量使用中文。代码、命令、路径、字段、固定协议值、必要专名及核对用的原文引文保留原样；首次使用必要缩写可附中文含义，后续不无故切回英文。

具体指标及执行合同统一维护在 [quality-rules.md](quality-rules.md) 和 `quality-rules.json`，由 `quality_rules.py` 按负责技能及阶段筛选。标准、厂商实践、用户规则和Luz本地门槛分开；当前规则检查器验证覆盖与文件完整性，领域审阅验证观察，用户批准正式业务文件。

## 五、交接与失效

每次交接包含：当前版本、输入哈希、职责范围、已验证结果、未覆盖项、下一步和阻塞原因。稳定映射为需求→功能→页面→组件→动作→接口→用例→证据。输出是可执行资料；内部审计编号、路径和检查计数不展示在产品界面。

框架、需求、组件源码、许可、批准范围、配置、依赖、产物或审计代码变化时，只重开受影响链路，并重新绑定当前证据。新一次通过不能掩盖已有失败；修改前失败单独记录，回归必须区分。

验证器能发现结构缺失、未知引用、哈希变化、部分绕过和实际运行失败。它不能独立证明来源相关、许可适用、人工身份、视觉美观或不存在所有缺陷。因此最终检查必须结合自动证据、语义审阅与用户对正式文件的审核。

## 六、持续执行

用户要求持续目标时，用所在平台的持续任务机制建立目标，目标里写明可验证的完成条件。常规依赖、可逆修改与已授权验证连续执行；遇到必须由用户决定的具体审批，准备好实物和问题再交接。没有时间预算不自创预算；不把尚未完成的流程标记为完成。持续目标不等于无人值守发布授权。

经验回流是可检验的维护闭环：记录症状与适用范围 → 找到根因和反例 → 修订唯一规则源/实现 → 运行有区分力的回归 → 用另一种说法检索 note → 后续真实任务复核。确认次数、抓取量和规则长度不能表示准确率。偏好标明全局/项目/当前会话范围，过期或被新要求替代的条目不得继续全局强制；无法判断范围时作为待核对资料。规则标题、路径、生成器或数据合同变化后，检查所有受影响规则卡和注册入口，防止文档改名使调用失效。

维护后运行 `python -X utf8 D:\Codes\Luz-Project\scripts\skill_contracts.py`：它只读地检查七个技能的入口、共享合同链接、共同硬规则、四套规则卡、共享代码块和本机注册，再运行受影响技能的回归。通过只说明这些结构没坏，不代替实际任务的评估。规则卡核心与经验库存取是同一段代码的四份副本，只在 Luz-Design 改，用 `sync_rule_core.py --write` 同步。全局入口块只在 `Luz-Dev/scripts/register_skills.py` 里改，再用它写入，不手改托管块。
