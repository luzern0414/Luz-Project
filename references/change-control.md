# 需求变更台账（全局维护）

项目一旦有客户新增需求、修改规则、补充细节、删除功能，**先登记再动手**。台账是全项目唯一的变更来源：`data/changes.json` 是事实，`docs/01-需求对接/06-需求变更台账.xlsx` 每次自动重排，交付时冻结一份快照。

## 触发与登记

用户说下面这些话时，立即登记（缺信息先问清楚，再登记，不能只写“修改规则”）：

| 用户说 | 类型 | 例 |
|---|---|---|
| 客户新增需求 / 加一个功能 | 新增 | 增加储值充值，档位 200/500/1000 |
| 客户修改规则 / 改一下口径 | 修改 | 积分 100 分抵 1 元改为 50 分抵 1 元 |
| 补充一个细节 / 客户又说 | 补充 | 核销超时为预约结束后 30 分钟 |
| 不要这个功能了 | 删除 | 取消分销功能 |

```powershell
py -X utf8 D:\Codes\Luz-Project\scripts\project.py change <项目> add --type 修改 --category 规则 `
  --title "积分抵扣比例调整" --detail "100 分抵 1 元改为 50 分抵 1 元；历史积分按新比例抵扣，不追溯订单" `
  --source 客户 --requester "店长" --refs FN-002 --affects proposal,architecture,technical-plan `
  --status 已确认 --confirmed-by "店长（微信确认）" --feature-ops ops.json
```

- 字段：分类（需求/规则/界面/流程/技术/范围/其他）、来源（客户/内部/测试发现/政策法规）、关联功能 ID、影响阶段、影响说明（工期/成本/风险）、是否进客户台账（`client_visible`，见下）。
- `--detail` 必须写变更后的**具体逻辑**，包括边界、例外、是否追溯；这是后续开发与验收的依据。**`detail` 是客户读的文字**：写客户的话，不出现技术词、内部编号（审批编号 APPROVAL-…、产物编号 ART-…、底座项 STK-/FE-/BF-…）和其他文件的名称（《功能清单》《业务逻辑确认表》等）。审批编号、阶段名、出处、谁在什么时候怎么处理的这类**过程记录写进 `--note`**（存在 `note` 字段，按日期逐行追加），`note` 不进客户台账；`change update --note` 同样只追加到 `note`，不再改 `detail`。
- `--client-visible 是|否|默认`：这条变更是否出现在交给客户的 `06-需求变更台账.xlsx` 和交付快照里。**默认**（不写）：来源为客户、分类为需求/规则/范围的可见；内部、测试发现、政策法规来源，以及分类为界面、技术、流程、其他的不可见（它们只留在 `data/changes.json`，开发和验收照常使用）。写了就按写的：内部来源但客户确实该知道的写 `是`，客户提出但全是技术内容的写 `否`；`默认` 清除显式设置。可见的条目 `title`、`detail`、`impact` 含内部编号或其他文件名会被拒绝，改写成客户的话，或者标 `否`。
- 状态：待确认 → 已确认 → 已实施，或已驳回。客户口头提出但未确认的写“待确认”；有确认人和方式才写“已确认”（`--confirmed-by` 必填）。
- `--feature-ops`：已确认时自动改功能清单，`[{"op":"add|update|remove","feature":{"id":"FN-002","rules":"…"}}]`；改动会让该功能 `version` +1 并记录变更编号。**不得直接手改 features.json**：批准后的来源文件哈希变化会被 `check` 报错。

## 登记之后发生什么

1. 已确认且影响的阶段已批准：自动把最早的受影响阶段置为 `pending-review`，其下游批准全部作废（沿用哈希门禁）；变更条目记录被重开的阶段。
2. 待确认的变更：不改任何文件，但**阻断**所列阶段的审批，直到确认或驳回。
3. 功能清单改变后，方案说明书、系统架构图、功能清单与业务逻辑确认表标为“已过期”（来源哈希不一致），必须重新生成才能再审批；验收清单和使用说明在 handover 阶段同样检查。
4. 各技能重读 `project.py context <项目> <阶段> --skill <技能>`：`client.recent_changes` 与 `client.open_changes` 说明哪些内容已变，不能凭旧上下文继续。

## 各技能收到变更后做什么

| 影响 | 负责技能 | 动作 |
|---|---|---|
| 功能范围、规则 | Luz-System | 更新功能清单与架构/页面动作，重新核对原型闭环 |
| 界面、交互 | Luz-Design | 更新 UI 交接与组件状态，重新做视觉检查 |
| 接口、数据、业务逻辑 | Luz-Dev | 更新合同、迁移与测试；规则类变更同步配置与回归样例 |
| 验收、测试 | Luz-Ops | 重跑受影响的检查与回归集；更新验收项证据 |
| 客户文档文字 | Luz-Writing | 改写受影响章节，不改未变化的部分 |

## 台账 Excel

由 Luz-Design 的 `make_xlsx` 生成：单工作表、无序号列、冻结表头；列为变更编号、提出日期、类型、分类、标题、逻辑与补充细节、来源、提出人、关联功能、涉及阶段、影响说明、状态、确认人、确认日期。尚未选定文档主题时只写 JSON，不生成 Excel（先 `client theme`）。

- **只含客户可见的条目**（`client_visible`，默认规则见上）；内部变更、技术和界面变更、被标 `否` 的条目不进 06 和交付快照，仍在 `data/changes.json` 和 `change list` 里。`change render` 会报告可见和仅内部各几条，并列出可见条目里仍含内部编号或其他文件名的文字（旧数据只报告，不改写）。
- **日期按北京时间**：提出日期取登记当天（北京日期）；`confirmed_at` 存的是 UTC，台账里的确认日期按 +08 换算成北京日期（UTC 11-03 23:15 显示 11-04）。提出日期和确认日期都是日期型单元格，未确认的确认日期写“—”。
- 旧版本在 `detail` 末尾追加的 `[日期] 过程记录` 行，渲染客户台账时不显示；自动登记的旧条目里“来自业务逻辑确认表的功能勾选（M02）；”这类前缀和提出人“客户（业务逻辑确认表）”也不显示（数据本身不改写）。新登记的条目 `detail` 不含这些，出处写在 `note`。
- `change update <编号>` 可以不改状态，只改 `--client-visible`、`--detail`（改写客户读的逻辑，原文自动记进 `note`）、`--impact`、`--confirmed-by`（给没有确认人的已确认条目补上）、`--note`。

交付：`change update --all-confirmed --note "随版本 V1.0 实施"` 把已确认变更标为已实施（逐条确认对应功能已上线后再批量执行），`change snapshot` 冻结台账；交付门禁要求没有待确认、已确认未实施的条目，且快照哈希与当前台账一致。
