# 商业系统项目路线

项目经理先明确客户要办成的事、项目负责人、决策人以及哪些使用端参与。把收到的需求、业务单据、现行规程、字段字典和脱敏样本原样归档到 `docs/01-原始资料`。每一份对接件归入 `02-对接资料`，工程说明与原型归入 `03-开发资料`。过程稿、调研和审批保存在状态根。文档目录在项目整个期间保持稳定。

## 三次确认和实施基线

| 时点 | 项目团队做什么 | 这次要决定什么 |
|---|---|---|
| 范围与方案 `scope` | Project 给 System 项目背景。System 从角色、现行流程和失败成本提出问题，由 Crawl 检索一手资料，记录已采用的结论。Writing 协助表达，Design 提供正式文档版式。一起出示 `02/01-需求说明.pdf` 和 `02/02-系统方案.pdf`。 | 确认使用者、关键目标、覆盖边界、外部依赖与成功条件。外部案例提供备选做法，待决规则列明确认人及业务影响。 |
| 功能与技术设计 `design` | System 按确认范围定义领域对象、模块归属、动作、权限和状态。Dev 确定数据、接口、集成、部署边界与风险。Design 梳理逐页信息与跨端状态，Ops 预审可测性。一起出示 `03/01-功能说明.html`、`02-技术方案.html`、`03-前端开发说明.html`、`04-后端开发说明.html`。 | 业务能否办完，异常能否恢复，外部系统怎样衔接，数据谁能看、谁能改，以及难点和质量目标能否验证。此时已经有足以指导原型和估计风险的架构。 |
| 操作走查 `demo` | Design 制作 `03/05-交互原型.html`。System 按第二批的功能编号核对岗位入口、操作和数据；Dev 核对记账时点与恢复规则；Ops 从各角色入口实际办理并查询结果。演练环境标注数据性质。 | 用户能逐项查询、建单、处理、复核和追溯。每个已确认的前端功能均有实际操作与可见结果。依赖硬件、生产身份或真实外部服务的验证条件及预期结果写入第二批功能说明。 |
| 定稿 `baseline` | System 汇总已确认的功能、规则与走查结果；Dev 核对架构，Project 确定实施依赖与负责人。产出 `02/03-架构图.pdf`、`04-功能需求清单.xlsx`、`05-业务规则确认表.xlsx`、`06-项目实施计划表.xlsx`。 | 把三次已确认的内容变成能排期、开发和验收的同一版资料。功能编号继续用于实现和测试。若出现新增功能、权限变化或业务结果变化，先回到受影响批次确认。 |
| 实施到运行 | Dev 接入真实服务、实现数据约束和迁移，留下构建、自测和回退步骤。Ops 独立复核目标环境，执行发布演练、监控与恢复验证。Project 核对当次生产授权、运维交接及客户签收。 | 交付对象、运行环境、验证结果、残余风险、负责人与当前版本均可复核。Demo 确认、生产发布授权、客户最终验收各自独立。 |

表中 02 和 03 分别指对接资料和开发资料。第一批统一审两个成品，第二批统一审四个成品，第三批审一份可操作原型。一次拒绝可以只指出一个文件、一条规则或一个场景，修订后复查受影响的整批版本。

## 让架构足以支撑商业运行

从实际业务列出发起人、受理人、生效时点与异常接手人。逐模块核对组织与数据范围、跨端状态、异步任务、外部系统、历史记录和运维责任。业务负责人确认每个模块的适用规则。

| 项目场景 | 系统与技术设计至少要回答 | 适合在 Demo 和验收中演示 |
|---|---|---|
| 企业资源计划（ERP） | 谁维护主数据；业务单据何时记账；反审核、冲销怎样影响下游期间与对账。 | 从单据穿透到凭据，观察权限拒绝和已结账期间的处理。 |
| 仓储管理（WMS） | 收货区和存储区分别记录什么数量？分配预占、复核、发运分别怎样影响同一库位与批次？谁可核准盘点差异？ | 查商品和库位，建入库单、收货、上架，看实物和可用增加；出库分配后查预占，发运后对流水。移库核对两侧数量，盘点差异交主管核准。 |
| 小程序与 App | 登录和角色如何绑定；弱网、中断和重复点击时保留哪些数据；手机与后台显示何时一致。 | 手机提交，后台受理，再回手机查进度。 |
| 智能体系统 | 工具以谁的权限运行；知识来源怎样过滤；有副作用的动作如何确认；如何取消、恢复和评测。 | 同一任务在有权、无权、依赖失效时走不同分支，保留动作结果。 |
| 管理及运营平台 | 门店、部门、租户间的数据范围；批量操作和导出由谁审批；指标的对象、时间窗、单位与口径。 | 运营人员切换数据范围、核对指标明细，观察授权前后的可用操作。 |

System 定业务含义与布局顺序，Design 定可见表现与操作反馈，Dev 对服务端实际结果负责，Ops 验证这次交付。纯视觉调整可留在当前批次；若把“已受理”改为“已生效”，应重开设计，重新验证所有消费该状态的页面、接口和用例。

### 原型验收

System 按已确认范围列出每个业务对象的查询入口、办理人、动作和保存后的结果。Design 将对象列表、详情、工作队列和业务表单接成可操作的页面。Ops 按功能编号留存操作前后的数据，并从第二处入口核对同一结果。

| 验收项目 | 检查动作 |
|---|---|
| 岗位与导航 | 从对应岗位进入业务模块。用商品、客户或单号查到对象，核对筛选范围、详情和返回位置。 |
| 办理与记账 | 从空表单新建业务。录入实际字段，提交后核对责任人、单据状态和资源变化。分开记录预约、受理和生效时点。 |
| 异常与恢复 | 制造缺少必填项、数量越界或依赖超时的情形，核对原因、可执行的补救动作和重复提交结果。 |
| 单据与流水 | 由单据查看关联记录，再从记录回到原单。涉及数量或余额时，逐项核对变动前后值。 |
| 功能覆盖 | 第二批功能台账是验收清单。每项原型功能绑定浏览器操作和实际结果。需在目标环境验证的功能，随第二次确认登记条件与预期。 |
| 页面与交互 | 在目标宽度打开列表、业务表单、校验状态和结果页，执行 [Design 成品要求](../../Luz-Design/references/design/hard-rules.md)。从打开到返回逐步检查。核对固定白色导航、独立办理页、实际颜色和图形图标，核对返回后的筛选、位置与焦点。 |

`build demo` 在状态根写入 `data/commercial/demo-walkthrough.json`。每条记录含场景、视口、操作、可见结果及 HTML 与 Design 检查程序的 SHA-256。确认前更改页面、走查记录或升级检查程序，均须重建本批。已确认版本保留原始记录。

场景可用 `hover`、`focus`、`press` 验证鼠标与键盘状态，`fill`、`select`、`click` 办理业务，`check` 核对中间结果，`reload` 检查恢复。走查应覆盖用户实际到达的状态，包括表单校验失败和只读角色。

成品文字直接写角色、动作、条件、业务结果与证据。提示指向下一步操作，例如“填写差异原因后提交”。制作过程、编辑批注和检索复盘归入状态根。

## 执行

1. `project.py init <名称> --project-dir <项目目录>` 建立完整项目。运行 `project.py next <项目>` 查看下一步，`project.py context <项目> <阶段> --skill <技能>` 取得专属上下文。只整理目录可使用 `scaffold`。
2. 用 `project.py templates <项目> scope` 选择首批成品模板，登记 `step <项目> scope rules`。由 System 调 Crawl 实际联网。以项目状态根为 session、`luz-system` 为 caller、`scope` 为 stage，使用项目共享任务目录。把真实模板选择交给检索阶段作为 `template_uses`；完成原文核验、结论与检查，再登记 `specialist` 的专业自检。各批次可用 `checklist` 获取准确命令。
3. 领域技能填好[批次输入样例](../templates/商业项目批次/README.md)。调用 `project.py build <项目> scope --data <范围事实.json>` 生成一批，对照 `next` 核查整批成品。后面三批相同，参数分别用 `design`、`demo`、`baseline`。
4. 前三批由用户明确确认后，执行 `project.py approve <项目> <阶段> --approver <确认人> --note <原话>`。有修改意见先记反馈，回到持有相关决定的角色修改，重建后重新展示。正式授权绑定对应一组输出。已经进入实施的变更登记在项目变更台账。
5. 基线形成后通过 `next`、`checklist`、`render` 和 `check --strict` 跟踪实施、验收、发布与交接。按终端与风险选择实际测试。实测通过、风险接受、不适用和未测分别列示。

旧项目从 `project.json` 识别原流程，继续使用原有文档、审批记录及阶段路径。独立的 UI 改版、排版、检索和仓库检查沿用各自入口。
