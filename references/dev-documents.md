# 开发文档标准

给开发看的文档放在 `docs/02-产品开发/`，是 HTML。本页是这些文档的唯一标准：叫什么、写哪几章、每章必须有什么、事实从哪来、怎么检查。校验器在 `scripts/dev_documents.py`，写文档的命令是 `project.py document <项目> <阶段> --file <spec.json>`；不符合标准的文档写不出来，也不能审批。

给客户的文件（方案说明书、系统架构图、功能清单、确认表等）不在这里，见 [client-documents.md](client-documents.md)。

## 1. 四份文档与命名

文件名固定为“两位序号加中文名”，序号决定阅读顺序，名字写它回答什么问题。不再写 `architecture.html`、`xxx-review.html` 这种英文名，也不为每个阶段写一张空的概况页；总览是 Project 会话根的 `NNN-主题.html`，它链接到下面的文档。

| 阶段 | 文件 | 回答什么 | 读者 |
|---|---|---|---|
| architecture | `01-系统架构.html` | 系统由什么组成、怎么部署、关键问题怎么解决、为什么这样选 | 开发、运维、技术负责人 |
| design | `02-前端界面设计.html` | 每个前端（小程序、手机页、管理后台等）的页面长什么样、怎么交互、用什么词和组件；所有页面路径在哪 | 前端开发、设计、验收 |
| technical-plan | `05-后端设计规范.html` | 后端怎么分层、接口怎么写、库表怎么建、规则落在哪、怎么配置和测试 | 后端开发、测试、运维 |
| implementation | `06-实现报告.html` | 做了什么、对应哪些功能、测试结果、还差什么 | 项目负责人、验收 |

目录布局见 [project-structure.md](project-structure.md)：docs 的三个目录都只有一层，不建子目录；`project.py check` 会报出多余的子目录、放错位置和放错类型的文件，旧项目运行 `project.py migrate` 预演、`--apply` 搬家。**`docs/02-产品开发/` 放开发阶段的 HTML**，用一个序号顺序：`01-系统架构`、`02-前端界面设计`、各前端的原型（`03-手机原型`、`04-后台原型` 这样，序号加前端名称加“原型”，有几个前端就几个；小程序项目是 `03-小程序原型`）、`05-后端设计规范`、`06-实现报告`、`07-验收测试评审`、`08-发布评审`、`09-运维评审`（后三份是 Luz-Ops 的测试、发布、运维证据页）。需求、调研、方案、客户信息、交付这几个阶段的评审页是内部记录（用户不审阅、不被要求看），不进项目目录的 docs，放状态根的 `reviews/`（`01-需求评审`、`02-调研结论`、`03-方案评审`、`04-业务逻辑确认评审`、`05-交付评审`）。

## 2. 共同规则

1. **先核对依据，再生成。** 每份文档需要本阶段的 Crawl 前置记录。本地阶段记录依据并通过检查，联网阶段先读正文并生成结论。联网采用的结论进入文档末尾的“来源与依据”表。来源的 `id`、网址、归档哈希绑定本阶段记录；`finding` 必须准确取自已采用 finding 的 `summary` 或 `quote`，`applies_to` 必须对应该 finding 或通过其 finding ID 连接的 coverage。填写真实 `finding_id` 也不能授权自写结论或扩大采用范围；本次推导先以 `kind: decision` 登记依据再采用。
2. **事实来自代码和数据文件，不凭记忆**。接口清单、库表和字段从控制器和迁移脚本里提取，列出来之后与提取结果逐项核对；功能编号来自 `features.json`；数字（接口数、表数、测试数）写成提取出来的值。文档与代码不一致时，写进“已知限制”或“规范偏差与待办”，不悄悄抹平。
3. **结构固定**。architecture、design、technical-plan 三份文档用顶部标签页分类（有子标签的再分子标签），标签页、子标签、其中的章节标题和顺序见第 3 节；校验器逐个核对，多一个、少一个、换顺序都不通过。implementation 仍是平铺的章节。技术底座的内容（技术栈、前端规范、基础功能）不在文档里重写：每一类用 `baseline` 块列出底座规定和本项目的取值、状态、理由，规则见 [tech-baseline.md](tech-baseline.md)；项目的每个功能是一张 `function` 功能卡。
4. **开头是结论**。第一个二级标题是“结论”，一两句话说清这份文档的结论和适用范围，不是目录，不超过 150 字。
5. **图和表都有题**。表题在表上方写“表 N　名称”，图题在图下方写“图 N　名称”，编号全文连续；表头与列对齐；没有内容的单元格写“—”，不留空。
6. **图只画关系**。节点写名称加一句作用，线是单向的并说明传什么；一张图一个层次；图下的表或正文逐项解释，图上不写长句。支持四种图：分层图（`layers`）、步骤图（`steps`）、时序图（`sequence`）、关系图（`grid`）；图内文字不小于 14 像素。
7. **界面只用已核验完整来源的可交互原型，不放截图**。前端页签内嵌关联 Design 会话中按实际 mode 经过 build/audit/review/check 的入口；component-reuse 按组件合同装配，显式 source-locked 才限定仅改允许文字。截图只能作参考，不能冒充已运行的完整 UI 包。页签不额外显示截图、图题、来源说明和操作段落；机器字段 `prototype.source` 必填。与需求的差异写进“检查与差异”，关键缺口阻塞后续工作。原型访问页路径、导航结构和页面清单（含路由路径）全部写在“前端规范”的“页面与路径”里。
8. **不写待办标记**。含“待补充”“待填写”“TODO”“TBD”“XXX”“示例文字”“（略）”的文档写不出来；确实没做的事写进“已知限制”或“未完成与风险”，说明现状和影响。可以描述“配置里还是占位值”这类事实，不能留占位内容。
9. **版式由 Luz-Design 保证**。阅读型网页，一个一级标题、二级标题紧跟其后，正文表格按列对齐，一条字体栈；字号按 Markdown 的层级分两套，桌面（768 及以上）正文 18、手机正文 16，标题与表格的档位见 Luz-Design 的 `file-design.html` 网页文件 › 排版参数，页面样式取 `scripts/reading_style.py`（内嵌的原型沿用产品字阶，图里文字仍不小于 14 像素）；写完用 `check_document.py` 检查，零错误才交给用户审阅。
10. **文字用业务词和技术词各取所需**。开发文档可以出现接口路径、表名、类名，但第一次出现时用一句话说它是什么；界面用词表里的词（会员、套餐、课程、已预约）与界面保持一致。

## 3. 每份文档的标签页与必须有的内容

三份文档的页面结构一样：标题、结论，然后是顶部标签页；有子标签的标签页再分一排子标签。键盘左右键切换，地址 `#tab=1.2` 可直接指向某个子标签，打印时全部展开。表格只列项目事实，底座内容由 `baseline` 块并排显示。

**`baseline` 块**：一张五列表“项｜底座规定｜本项目｜状态｜理由”，状态是沿用、调整、新增、不用。同一类里底座的必有项一项不能漏（校验器逐项核对）；调整和不用要有理由、调整和新增要有本项目取值；项目自己加的项编号用 `X-` 开头且状态只能是新增。文档里的每一行必须与项目的 `data/baseline.json` 一致，该文件自己也要通过底座校验（`stack`、`frontend` 按底座项编号，`modules` 按基础功能模块编号，每个都要表态）。

**`function` 功能卡**：项目的每个功能（`features.json` 的 FN 编号）一张，放在所属模块的子标签里，写前端逻辑、后端逻辑、数据库、技术方案（每项至少 60 个字，写到真实的页面、接口、表和数字）、业务规则、异常与提示、测试各至少一条；有对应的基础功能写 `inherits`（如 `BF-LOGIN-01`），状态是沿用、调整或新增，调整要用 `change` 写清与底座哪里不同；与功能清单不一致的地方写进 `deviation`。

### 01-系统架构

结构参照 C4 模型（上下文、容器、部署、动态图）和 arc42（上下文与范围、构件视图、运行视图、部署视图、横切概念、架构决策、质量要求、风险与技术债），每个标签页回答一类问题，对应 ISO/IEC/IEEE 42010 的“架构描述按视图回答相关方的问题”。全文至少 3 张图。

| 标签页 | 子标签或章节 | 必须有 |
|---|---|---|
| 技术栈 | 技术栈总览 | 一张分层图（前端、后端、数据、部署、运维各用什么）；一张表：层、选择、版本、理由、放弃的备选；版本取自构建文件，不取自旧文档 |
| 技术栈 | 前端（小程序）、前端（管理后台）、后端、数据库、缓存与队列、文件存储、部署、运维观测、安全、测试与发布 | 每层一个子标签，一张底座对照表（`baseline` 块，scope 是该层编号）。项目的功能清单里没有小程序功能时，不出“小程序前端”这一子标签，其余层的底座对照表里也不出小程序专属的文字（见 [tech-baseline.md](tech-baseline.md) 规则 6、7） |
| 总体架构 | 系统上下文 | 一张分层图：使用者、使用端、外部系统；一张表说明每个使用者做什么 |
| 总体架构 | 分层与部署 | 一张部署图（服务器上跑什么、之间用什么协议）；一张表说明每个节点 |
| 总体架构 | 业务模块 | 一张表：模块、作用、对外接口、数据表、依赖；写明模块之间的调用规则 |
| 总体架构 | 关键技术方案 | 每个关键问题一小节：问题、做法、防线或步骤、测试；至少一张时序图或步骤图（预约、核销等） |
| 功能与技术方案 | 每个功能模块一个子标签（与 `features.json` 的模块一一对应、同名同序） | 模块说明；该模块每个功能一张功能卡 |
| 决策与质量 | 架构决策 | 一张表：决策、背景、选择、放弃的方案、代价、状态；每条决策能在代码或配置里找到落点 |
| 决策与质量 | 质量属性 | 一张表：性能容量、可靠性、安全、可维护、可观测，各写目标数字和做法 |
| 决策与质量 | 演进与扩展、已知限制 | 将来要加什么、现在留了什么口子；已知的限制、与设计的偏差、需要用户决定的事 |

**随附产物：界面功能说明与入口表（有界面的项目）。** 架构文档本身不设前端页签。界面的功能层——页面与路由、入口、标签栏项数与名称、组件清单、按钮动作、状态、数据需求、文案键，不含任何视觉值（见 Luz-Design `references/ui-ownership.md`）——写在**界面功能说明**里，由 Luz-System 在架构阶段交出，和架构文档一起登记为本阶段的产物，受哈希保护（批准之后改它，批准自动失效，要先登记变更）。文件放在状态根下，建议用 `architecture/frontend-spec/`；登记命令 `project.py artifact <项目> architecture <文件> --kind <类型>`：

| 类型（kind） | 文件 | 说明 |
|---|---|---|
| `ui-requirements` 或 `frontend-spec` | `ui-requirements.json` | 新组件复用项目采用 [System 的动作归属合同](../../Luz-System/references/handoff.md#动作归属与业务规则)。已登记的旧项目可以按原合同复核 |
| `frontend-spec-page` | `界面功能说明.html` | 人读的版本，由上面的数据生成，不手改 |
| `entrances` | `entrances*.json` | 入口表，每个使用端或角色一份；用 Luz-System 的 `entrances_check.py <入口表> --features data/client/features.json` 逐份检查 |
| `proto-logic` | `proto-logic*.json` | 功能所需行为、场景与演示数据，供核对来源已有能力与记录缺口（可选；不授权重画来源 UI） |
| `frontend-spec-notes` | `decisions.md` | 界面功能说明的取舍与决定（可选；界面功能说明里“见决定记录”指向它） |

审批前（`project.py approve --doc`，作为内部步骤 `records`/`build` 的一部分）核对：有界面的项目（功能清单里有任何使用端的功能）缺少界面功能合同、界面功能说明或入口表，或各份入口表合起来没有覆盖仍在项目里的每个功能（每个功能要有一行入口，或在 `no_entrance` 里写明为什么没有），就不能批准。功能卡的“前端逻辑”从界面功能说明取页面编号、路由、入口和动作编号，与它逐项一致，不另写一份；正文标明这些本地依据的文件名与所在文件夹（`check_document.py` 不允许页面里出现 `raw/` 路径，完整路径在产物登记表 `data/artifacts.json` 里）。设计阶段只读它们：缺的、冲突的退回架构阶段，走变更台账。

### 02-前端界面设计

先写清前端的规范（对照底座逐类写本项目的取值，并把所有路径写在“页面与路径”里），再给每个系统、每个设备端一个标签页，页签里只有一个能直接点的可交互原型，最后写检查与差异。

这一阶段先读 `luz-design` 的规则卡 `design-path`，首页与常见页面的范式、入口归属与去重读 `page-patterns`：拿 architecture 阶段交来的入口表 `entrances.json` 和功能清单跑 `page_pattern.py` 的 `brief`、`plan`、`check`，成品页再跑 `check-page`；设计不增删功能与入口，缺的、冲突的退回 architecture。

用户明确要求严格沿用已有界面时，规则卡、页面范式和下面的底座表只用于对照并记录原件的真实取值与缺口，不据此改原件的结构、字体、布局、配色和交互；原件没有的主题、状态、平台能力不写成已实现。

标签页 = **前端规范 + 每个前端一个页签 + 检查与差异**。页签名就是前端的名字（手机页、管理后台、小程序、平板页……），由 spec 声明：有小程序和管理后台就是 4 个页签，只有后台就是 3 个；有多个系统就各开一个；同一个系统的手机页、电脑页等不同设备端也分开各开一个（手机页和后台可以都属于“网页管理后台”这种使用端，仍是两个页签）。

| 标签页 | 子标签或章节 | 必须有 |
|---|---|---|
| 前端规范 | 设计原则、前端技术栈、前端逻辑、字体、色彩、卡片与容器、图标、布局与响应式、动效、交互与反馈、文案与用词、图片与素材、可访问性（13 类，与底座一致） | 每类一个子标签，一张底座对照表（scope 是该类编号）。按实际来源填写：技术栈与组件、页面地图与交互契约、路由与权限、请求与会话、状态位置、字阶与配色、卡片与图标、断点、已有动效及素材，逐项连接来源文件、已采用 finding 或真实检查记录。仅记录原件实际提供的主题、切换方式和对比度结果；原件没有深色、跟随系统或主题切换时记录缺口，不套主题库补造。文案只登记已核验、允许替换的文字及采用位置；未知项标明未核实，关键缺口阻塞 |
| 前端规范 | 页面与路径（不是底座类别，排在 13 类之后） | **所有路径只写在这里**。每个前端一节（`sub` 块，文字是前端名称），每节有：原型文件路径（如 `docs/02-产品开发/04-后台原型.html`）；导航结构表（菜单、入口、角色权限）；页面清单表（至少含“路径”列：路由路径、页面、作用、主要接口、角色），页面场景表可再加。校验器逐个前端核对：有这一节、有 2 张以上的表、页面清单有“路径”列、写了原型文件路径 |
| 每个前端（页签名是前端名称） | — | 只有一个 `prototype` 块：浏览器框或手机框里的真实界面，加“重新载入”“在新窗口打开”两个按钮。**不放**说明段、页面清单、导航表、截图、图题、来源、“可以这样试” |
| 检查与差异 | 原型与真实系统的差异 | 写明原型比真实系统多了什么、少了什么，以真实系统为准；不提截图 |
| 检查与差异 | 界面检查 | 表：检查项、标准依据、现状与证据位置；逐项记录真实浏览器覆盖的页面、视口、主题、交互和错误，以及已测通过、已测失败或未测。手机可操作、控制台零错误、减少动态效果等结论必须有对应实测；原件未提供的能力记缺口，不能默认宣称通过 |

**前端规范 13 类谁填**：功能要求归 Luz-System、完整来源选用与视觉核验归 Luz-Design、技术兼容性归 Luz-Dev（对照表见 Luz-Design `references/ui-ownership.md`）。System 提供已确认的页面、入口、交互与文案要求；Design 对照原件记录字阶、配色、卡片、图标、响应式、动效、素材、主题及可访问性；Dev 核验原件框架、组件和依赖能否用于已确认实现。默认组件模式按功能合同选真实框架和组件并验证整体；新控件依组件合同处理具体批准。显式来源锁定时才要求原件不新增 UI/交互，冲突先换来源或记缺口；两种模式都不能略过关键功能缺口。

**前端页签怎么在 spec 里声明**：`tabs` 依次是前端规范、各个前端页签、检查与差异；中间每一项长这样（章节只有一个，里面只有一个 `prototype` 块）：

```json
{"title": "手机页", "layout": "frontend", "surface": "web-admin",
 "sections": [{"title": "手机页", "blocks": [{"type": "prototype", "file": "docs/02-产品开发/03-手机原型.html", "title": "手机页原型（销售）", "kind": "phone",
 "source": {"session": "<真实关联 Design 会话绝对路径>", "package": "raw/source-ui", "entry": "<已审计入口>"}}]}]}
```

- `title` 是页签名，也是“页面与路径”里那一节的名字；页签名不能重复。
- `surface` 是这个前端属于功能清单里的哪种使用端：`miniprogram`、`web-admin`、`agent`、`website`、`mobile-app`。功能清单里有的使用端每种至少要有一个页签，没有的使用端不出页签；同一种使用端可以有多个页签。页签名是旧标准的“小程序”“管理后台”时可以不写 `surface`（按名字推断为 `miniprogram`、`web-admin`），其他名字必须写。小程序的原型 `kind` 只能是 `phone`。
- `prototype` 块写 `file`、`title`（原型框顶栏的名字）、`kind`（`phone` 或 `wide`）、`source`，可选 `height`；**不写** `caption`、`try`、`sources`。不同前端不能用同一个 `file`。`source` 严格只有 `session`、`package`、`entry` 三项，分别指真实 Design 会话、其 raw 中的完整包、`ui_package.py check` 按实际 mode 返回的已审计入口。`library`、组件前缀、文件大小或占位 source 不能取得来源资格。
- 前端页签和“前端规范”“检查与差异”里都不能有 `image` 块（截图）；`prototype` 块只能出现在前端页签里。
- 联网阶段在页签后列 `sources`（“来源与依据”表），填写至少两条实际采用的结论。本地阶段写清正文依据，`sources` 保持空数组。

**界面包怎么进项目**：新界面默认按 Design 的 [组件复用合同](../../Luz-Design/references/component-reuse.md) 做成完整界面包（`frontend.py init → seal → review → check`），留在关联的 Design 会话 raw 里；`prototype` 块的 `source` 指向它。

- 包里的入口、样式、脚本、字体、图片、依赖和许可保留完整文件树与相对引用，在关联 Design 会话 raw 中核验，不把入口单独搬走，也不压平。Design 会话的 MANIFEST 必须关联当前项目状态根和 design 阶段，并用 `project.py session` 登记为本项目的 luz-design/design 会话。
- `prototype.file` 是 Project 用 Luz-Design **`reading-html`** 真实模板生成的静态访问页：先按具体路径 select，生成后 post 绑定最终哈希。设计图册的 iframe 直接指向包里已审阅的入口。访问页的模板、入口、回执、审阅摘要、包的完整性与项目关联在出示和审批时重验，登记任意 HTML 不能替代它们。
- `kind: phone/wide` 只控制浏览器预览尺寸。响应式 Web 原型不等于原生小程序、原生 App 或已接入生产业务；原生 SDK、登录、支付、设备 API 等没有经过本次真实验证的能力写进限制，不从预览尺寸或名称推断通过。
- 已登记的来源锁定包（回执是 `luz-source.json`）继续按原合同核验：只核对原件已有的视口、外观、状态和交互，缺的能力记缺口，不往里插新代码。Design 现在没有新建这类包的工具；用户明确要求严格沿用已有界面时，按 Design [ui-ownership.md](../../Luz-Design/references/ui-ownership.md) 的来源锁定交接处理。

**独立获授权的旧原型/生产集成**继续其单文件、平台适配、演示数据、主题令牌和浏览器检查流程；该分支只在明确生产/旧维护范围内执行，不能扩大新来源锁定任务。项目审批保持已有合同，没有新增风格或许可确认。

### 05-后端设计规范

“规范”指开发时必须遵守的约定，加上这些约定在代码里的落点。

| 标签页 | 章节或子标签 | 必须有 |
|---|---|---|
| 技术架构 | 工程结构与分层 | 目录结构；分层表（层、职责、禁止）；一张请求处理顺序图 |
| 技术架构 | 编码与数据约定 | 至少 2 张表：编码规范（事务、金额、时间、枚举、日志）、建表约定 |
| 功能与业务逻辑 | 每个功能模块一个子标签（与 `features.json` 的模块一一对应） | 至少 2 张表：业务规则的落点与测试（规则、实现位置、测试）、提示文案与触发条件；有状态的模块再加状态与流转表；写明并发与一致性靠什么保证、涉及哪些表 |
| 接口 | 接口规范 | 至少 3 张表：路径前缀与鉴权、请求响应与分页导出约定、错误码和业务原因 |
| 接口 | 接口清单 | 按前缀分组的接口表（5 张以上），与代码提取结果逐项一致 |
| 数据库 | 数据库设计 | 一张关系图；至少 4 张表（每张表的字段、约束、索引，关键查询，迁移脚本清单） |
| 安全与运维 | 安全与权限 | 账号体系、会话、密码、锁定、越权防线、上传校验、敏感信息 |
| 安全与运维 | 配置与部署 | 配置分层、环境变量、容器与反向代理、备份与恢复 |
| 安全与运维 | 日志与审计 | 请求编号、日志字段与脱敏、操作日志、保留期 |
| 安全与运维 | 测试规范 | 测试分层、环境、覆盖的验收项、结果；测试怎么控制时间 |
| 底座对照与偏差 | 基础功能采用情况 | 一张 `baseline` 表：底座的每个基础功能模块，本项目沿用、调整还是不用及理由 |
| 底座对照与偏差 | 规范偏差与待办 | 表：规范要求、现状、影响、处理；与 Luz-Dev 标准对照得出的差距 |

## 4. 怎么生成

1. 在项目里按 [runbook.md](runbook.md) 第 4 节的顺序跑该阶段的 Crawl 前置检索：`crawl_preflight.py run`（要读的原文用 `--url` 指定），读正文，写补充信息，`conclude`，`check`。同一网址在两个阶段里各采一次，各是自己的存档，前一个阶段的存档保持原样、仍能核验；每个阶段登记自己采到的存档。
2. 读对应技能的规则卡：architecture 读 `luz-system` 的 `system-design`；design 读 `luz-design` 的 `design-path`、`page-patterns`、`interface-visual`、`interface-layout` 和 `luz-system` 的 `miniprogram`、`admin-list`、`interaction`；technical-plan 读 `luz-dev` 的 `backend-module`、`api-data`、`config-logging`；implementation 读 `luz-dev` 的 `project-handoff`。阶段路由（`project.py route`）会列出标准和这些卡。
3. 从代码取事实：接口、库表、配置、测试结果；原型的页面、字段和文案取自真实系统，不配截图。
4. 先写项目的底座表态 `data/baseline.json`（[tech-baseline.md](tech-baseline.md) 第 2 节），再写 spec（`data/stages/<阶段>.json` 的内容）：标签页、章节与块见 [dev_documents.py](../scripts/dev_documents.py) 的说明；来源表准确绑定已采用的 summary/quote 和采用位置。先为每份正式输出选择真实模板；设计阶段另备齐关联 Design 会话的完整来源包、审计与每个访问页的 `reading-html` 选择记录。
5. `project.py document <项目> <阶段> --file spec.json` 校验并生成 HTML（先校验标准、再渲染）。
6. 用 `Luz-Design/scripts/check_document.py` 检查页面，用提取脚本复核接口与库表。同阶段可在内部批量构建，所有内部门通过后才按顺序一次出示一个文件；用户通过后出示下一个，见 [runbook.md](runbook.md)。审批之后文档或它的来源数据再变，这个文件的批准自动失效，顺序在它之后的文件随之失效。

Ops 三份项目评审 HTML（验收测试、发布、运维）有两条正式生成路线：`project.py document` 使用同项目的 `luz-project/showcase` 记录，Ops 报告生成器使用同项目的 `luz-ops/showcase` 记录及 Ops writer 索引。双方门禁只对这三个准确阶段与路径核验相应真实 `phase=post`；错误阶段、其他 caller、跨项目记录或只有模板选择均不能替代。PDF 继续按各自既有 Ops 正式模板合同核验。

## 5. 标准的依据

| 依据 | 取自 |
|---|---|
| 架构文档按视图组织、图分层次 | C4 模型（c4model.com）、arc42（docs.arc42.org）、ISO/IEC/IEEE 42010（iso-architecture.org） |
| 多企业隔离写成可选方案及取舍 | 微软架构中心《多租户解决方案的租赁模型》 |
| 小程序界面的导航、反馈、热区 | 微信小程序设计指南（developers.weixin.qq.com/miniprogram/design） |
| 点击区域底线 | WCAG 2.2 的 2.5.8 目标尺寸（最小） |
| 接口错误与配置 | RFC 9457、OWASP API Security Top 10 2023、十二要素应用（各项目的“后端设计规范”里逐条说明采用与否） |

这些依据只回答“文档该怎么组织”；每个项目具体写什么，以那个项目自己的前置检索记录为准。
