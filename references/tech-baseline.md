# 技术底座

每个 Luz 项目都建在同一个底座上：同样的技术栈、同样的基础功能、同样的字体配色构图动效交互。底座在各技能里写一次，项目不重写，只在底座上说明“沿用什么、调整什么、新增什么、不用什么”，并写清理由。给开发看的三份文档（系统架构、前端界面设计、后端设计规范）都从底座出发：先展示底座，再展示本项目与底座的差别。

## 1. 底座是什么、写在哪里

| 底座 | 内容 | 文件 | 来源技能（内容的出处） |
|---|---|---|---|
| 技术栈 | 前端（小程序、后台）、后端、数据库、缓存与队列、文件存储、部署、运维观测、安全、测试与发布共 10 层，每项写规定、详细做法、理由、什么情况下可以换 | [baseline/stack.json](baseline/stack.json) | Luz-Dev（`backend/SPEC.md`、`operations.md`、`miniprogram.md`、`admin.md`）、Luz-System（架构分层） |
| 前端基础 | 设计原则、前端技术栈、前端逻辑（分层、路由、状态、请求）、字体、色彩、卡片与容器、图标、布局与响应式、动效、交互与反馈、文案、图片与素材、可访问性共 13 类 | [baseline/frontend.json](baseline/frontend.json) | Luz-Design（`visual-design.html`、`themes.json`）、Luz-System（`ui-standards.html` 与各端规范） |
| 基础功能 | 登录与账号、后台账号与权限、租户与门店、商品与套餐、订单、支付、会员卡与月卡、储值、优惠券、通知、文件、导入导出、审计、协议与隐私、统计、配置等模块；每个功能写前端逻辑、后端逻辑、数据库、技术方案、业务规则、异常、测试 | [baseline/functions.json](baseline/functions.json) | Luz-Dev（`module-specs/`、`backend/NN-*/MODULE.md`、`function-catalog.json`）、Luz-System（`function-list-design.html`） |
| 原型底座 | 可交互原型的运行底座：动效令牌、对话框与底部弹层、提示、骨架屏、场景配置面板、后台外壳与控件、图表 | `Luz-System/references/prototype-kit/` | Luz-System、Luz-Design（动效规则卡） |

底座文件由 `scripts/baseline.py` 校验（`python scripts/baseline.py`）：每一层、每一类都在，编号唯一，没有空字段和占位字样。底座的内容有变化时改底座，不改项目；项目的文档下次生成时自动带上新的底座。

## 2. 项目怎么在底座上改

项目在 `data/baseline.json` 里对每个底座项给出一行：

```json
{"baseline_version": "1.0",
 "stack":    {"STK-BE-01": {"status": "调整", "value": "Java 21 + Spring Boot 4", "reason": "客户的运维团队只维护 Java 服务"}},
 "frontend": {"FE-FT-01":  {"status": "沿用"}},
 "modules":  {"login": {"status": "调整", "value": "M01 登录与企业绑定", "reason": "只用微信标识加邀请码绑定企业，不取手机号"}}}
```

三张表各管一类：`stack` 和 `frontend` 按底座项编号（`STK-…`、`FE-…`）表态；`modules` 按底座的基础功能模块编号（`login`、`order` 等 18 个）表态，每个模块都要说明。项目里**每个功能到哪个基础功能**，写在系统架构文档的功能卡里（`inherits` 写基础功能编号如 `BF-LOGIN-01`，`status` 写沿用、调整或新增，调整要用 `change` 写与底座哪里不同），不重复写进 `data/baseline.json`。

**批准之后谁能改哪一段**：`data/baseline.json` 的三段分属两个阶段。`stack` 和 `modules` 属于架构阶段：架构阶段批准时把这两段的内容哈希（只算这两段，写作 `data/baseline.json#stack,modules`）记进该阶段的 `approved_sources`，之后无论谁改了这两段，`project.py check` 都报“阶段 architecture 批准后 data/baseline.json 的 stack、modules 两段已变化”，要先 `change add` 登记变更、重开架构阶段、重新批准；`frontend` 段（和 `baseline_version`）属于前端界面设计阶段，设计阶段改它不影响架构的批准，也不进架构的哈希。键的顺序、缩进不算内容。早于这条规则批准的架构阶段没有记录这个哈希，`project.py migrate` 会在架构文档与 `data/baseline.json` 逐行一致（状态相同）时补记当下的哈希，不一致就只提示、不绑定；`migrate` 不写审批记录，也不使任何已有批准失效。

| 状态 | 含义 | 要写什么 |
|---|---|---|
| 沿用 | 照底座做 | 不用写，文档里显示底座的规定 |
| 调整 | 底座有这一项，项目取值不同 | 本项目取值 + 理由（至少一句话说清为什么，来自客户约束、平台限制或评审结论） |
| 新增 | 底座没有，项目需要 | 编号用 `X-` 开头，写取值 |
| 不用 | 底座有而项目不用（可选项，或必有项经评审去掉） | 理由 |

规则：

1. **必有项不能不说**。底座里 `mandatory: true` 的项，项目必须说明状态；校验器逐项核对，漏一项就不能生成文档。
2. **调整和不用必须有理由**，理由不是“项目需要”，而是具体的约束或结论。
3. **偏离要集中看得见**：文档的“底座对照”表把调整、新增、不用的项列在一起；评审时先看这张表，其余沿用的项不必重读。
4. **项目不改底座文件**。发现底座缺项或写错，提给底座（改 `references/baseline/`），所有项目都受益。底座自己取材时发现的来源互相矛盾处记在 [baseline/CONFLICTS.md](baseline/CONFLICTS.md)，每处写了底座取哪一边；来源改对之后从那里删掉。
5. **功能卡**：项目的每个功能（`features.json` 的 FN 编号）在系统架构文档里是一张功能卡，写前端、后端、数据库、技术方案、业务规则；有对应的基础功能时写 `inherits`，只写与底座不同的地方。
6. **没有这一端就没有这一层**。小程序前端这一层（`frontend-miniapp`，7 项）和前端规范里只属于小程序的项（`surfaces` 只有 `miniapp`），只在项目的 `features.json` 里有小程序功能时才出现：文档里不出这一层的子标签，`data/baseline.json` 里不写这些项（写了会被校验器拒绝，提示“本项目没有这一端”）。`features.json` 还没有功能清单时（离线演练）一律按有处理。管理后台前端这一层每个项目都保留，因为网站和智能体平台的网页端也用同一套。
7. **底座正文不分端，分端的话单独写**。小程序层之外的底座项，`name`、`baseline`、`detail`、`why`、`replace_when` 的正文不写“小程序”“胶囊”“订阅消息”“wx.”；只对小程序成立的句子写在该项的 `by_surface.miniprogram`（字段名同正文字段），只有项目有小程序时才接在正文后面显示。校验器检查这条，写新底座项时直接按这个写。前端规范里 `surfaces: ["both"]` 的项是两端并排说明（表格里小程序与后台各一列），不受这条限制。

## 3. 三份文档怎么用底座

文档用顶部标签页分类，一页内切换，不滚很长一页；每个标签页里的表格只列项目事实，底座内容由 `baseline` 块自动并排显示。

| 文档 | 标签页 | 底座的用法 |
|---|---|---|
| 系统架构 | 技术栈 ｜ 总体架构 ｜ 功能与技术方案 ｜ 决策与质量 | “技术栈”按 10 层各一个子标签，每层一张底座对照表；“功能与技术方案”按模块分子标签，每个功能一张功能卡 |
| 前端界面设计 | 前端规范 ｜ 每个系统或设备端一个标签页（手机页、管理后台、小程序…） ｜ 检查与差异 | “前端规范”按 13 类分子标签，每类一张底座对照表，另有“页面与路径”子标签放所有原型文件路径、导航结构和页面清单；每个前端的标签页只放一个可交互原型，不放截图、页面清单和路径 |
| 后端设计规范 | 技术架构 ｜ 功能与业务逻辑 ｜ 接口 ｜ 数据库 ｜ 安全与运维 ｜ 底座对照与偏差 | “功能与业务逻辑”按模块分子标签，写业务规则、状态、异常、并发与事务、实现位置、测试 |

校验器逐个标签页、子标签核对标题和必须有的内容（见 [dev-documents.md](dev-documents.md)），并核对：底座必有项都已说明、`features.json` 的每个功能都有一张功能卡、每个模块都有业务逻辑子标签。

## 4. 做新项目的顺序

1. `project.py init` 之后读底座（本文与 `references/baseline/`），按客户需求确定用哪些基础功能和端。
2. 写 `data/baseline.json`：先全部标“沿用”，再逐项改“调整”“新增”“不用”并写理由。
3. 每个阶段前先跑 Luz-Crawl 前置检索，再生成文档；文档的基础内容来自底座，项目的事实来自代码、数据文件和真实运行的系统。
4. 评审时先看“底座对照”，再看项目专属的功能卡和业务逻辑。
